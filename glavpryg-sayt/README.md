# Главпрыг — сайт

Статичный сайт по адресу **https://mokeevasky.ru/glavpryg**. Отдаёт его nginx
напрямую, приложение в этом не участвует.

## Устройство

```
glavpryg-sayt/
├── public/                     исходники сайта (сейчас — заглушка)
│   ├── index.html
│   ├── styles.css
│   └── 404.html
├── deploy/
│   ├── nginx-glavpryg.conf     правила nginx → /etc/nginx/snippets/glavpryg.conf
│   └── vylozhit.sh             выкладка: файлы, правила, перезагрузка
└── tests/
    └── check-glavpryg.sh       проверка адреса снаружи, обычным запросом
```

Сайт лежит на сервере в `/var/www/glavpryg` под root с правами «всем читать,
никому не писать». Прямо из репозитория он не отдаётся: домашний каталог закрыт
для `www-data`, а открывать его нельзя — рядом рабочие каталоги проектов и
загруженные файлы.

Врезка в домен — одна строка `include /etc/nginx/snippets/glavpryg.conf;` внутри
server-блока `mokeevasky.ru`; сам блок версионируется в
`webui/deploy/nginx-webui.conf` и раскладывается `webui-deploy`.

## Первая установка (два шага под sudo)

    sudo bash glavpryg-sayt/deploy/vylozhit.sh
    sudo cp webui/deploy/nginx-webui.conf /etc/nginx/sites-available/webui
    sudo nginx -t && sudo systemctl reload nginx

**Порядок важен.** Сначала сниппет (его кладёт первая команда), потом конфиг
домена: наоборот `nginx -t` упрётся в отсутствующий `include`, и конфиг не
применится вовсе. Первая команда сама проверяет, есть ли врезка, и, если её
ещё нет, останавливается кодом 2 и печатает оставшийся шаг — испорченного
состояния при этом не возникает.

## Каждая следующая выкладка

    sudo bash glavpryg-sayt/deploy/vylozhit.sh
    bash glavpryg-sayt/tests/check-glavpryg.sh

Второй шаг больше не нужен: врезка в домен ставится один раз.

## Когда придёт архив с исходниками

1. Распаковать в `public/`, заменив заглушку (`index.html` должен оказаться
   в корне `public/`).
2. Выложить: `sudo bash glavpryg-sayt/deploy/vylozhit.sh`.
   Если сайт распакован не в `public/`, каталог указывается доводом:
   `sudo bash glavpryg-sayt/deploy/vylozhit.sh /путь/к/сайту`. Одну вложенную
   папку (архивы часто так и распаковываются) скрипт находит сам.
3. Проверить: `bash glavpryg-sayt/tests/check-glavpryg.sh`.
4. Если в архиве есть сборка (`npm run build` и подобное), выкладывать нужно
   каталог сборки, а `dist/` и `build/` из git исключены корневым `.gitignore` —
   в репозитории остаются исходники, на сервер уезжает собранное.

## Проверка

`tests/check-glavpryg.sh` ходит по настоящему адресу и смотрит шесть вещей:
главная отдаётся и **совпадает по хэшу** с `public/index.html` (сравнение по
хэшу, а не по строке из вёрстки, — чтобы проверка пережила смену заглушки на
настоящий сайт); `/glavpryg` уводит на `/glavpryg/`; несуществующая страница
даёт 404 своей страницей; заголовки безопасности на месте; HTTP уводит на HTTPS;
`/Claude/login` по-прежнему отвечает — выкладка сайта не задела интерфейс.

До первой выкладки проверка обязана падать: адрес отдаёт 404. Этим она и
проверяется сама (правило 12).

## Грабли

- **`add_header` внутри `location` отменяет наследование серверных `add_header`** —
  и не по одному, а всех сразу. Поэтому три заголовка безопасности в
  `nginx-glavpryg.conf` повторены дословно. Потерять их легко и незаметно:
  у интерфейса они останутся, у сайта пропадут.
- **`location = /glavpryg` без слеша** обязателен: иначе браузер считает
  страницу файлом и относительные ссылки уезжают в корень домена
  (`/styles.css` вместо `/glavpryg/styles.css`).
- **`Cache-Control: no-cache`** стоит намеренно: имена файлов без отпечатка
  содержимого, и закэшированная страница у посетителя пережила бы правку сайта.
  Появится сборка с отпечатками в именах — статику можно будет закэшировать
  надолго.
