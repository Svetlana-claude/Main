# VPN-сервер на своём сервере

Комплект для WireGuard: установка сервера одной командой, выдача и отзыв клиентов.

> **Состояние на 12.09.2026: сервер поднят и работает.** `46.8.178.196:51820/udp`,
> адрес в туннеле `10.8.0.1`, служба `wg-quick@wg0` активна и в автозапуске,
> транзит пакетов включён, правила `iptables` применены. Заведены два клиента:
> `notebook` (`10.8.0.2`) и `phone` (`10.8.0.3`), конфиги — в `exchange/vpn/`.
>
> **Со стороны сервера проверено всё, что можно проверить изнутри.** Не проверено
> то, что видно только снаружи: доходит ли UDP до порта через брандмауэр хостера
> и идёт ли трафик через туннель. Это показывает первое подключение клиента —
> см. «Проверки после установки».

---

## Почему WireGuard

| | WireGuard | OpenVPN | IPsec/IKEv2 |
|---|---|---|---|
| Настройка | конфиг в 10 строк | десятки параметров, свой центр сертификации | самая капризная |
| Скорость | в ядре Linux, быстрее прочих | в пользовательском пространстве | в ядре |
| Клиенты | Windows, macOS, iOS, Android, Linux — официальные | есть | встроен в системы |
| Расход на слабой машине | минимальный | заметный | средний |

При 2.9 ГБ RAM и профиле «доступ для себя и пары устройств» выбор однозначный.
Единственный минус WireGuard — работает по UDP и узнаваем при разборе трафика:
там, где UDP режут (гостиничный Wi-Fi, корпоративная сеть, блокировки по стране),
он не поднимется. Что делать в этом случае — в разделе «Если не работает».

## Что делает установка

1. ставит пакеты `wireguard` и `qrencode`;
2. создаёт ключевую пару сервера в `/etc/wireguard/` (права 600, только root);
3. пишет `/etc/wireguard/wg0.conf`: адрес `10.8.0.1/24`, порт `51820/udp`;
4. включает транзит пакетов (`net.ipv4.ip_forward`) — без него клиент подключится,
   но интернета через сервер не увидит;
5. добавляет правила `iptables`: пропуск транзита и подмена обратного адреса
   (MASQUERADE) на внешний;
6. открывает порт в `ufw`, **если тот уже включён**;
7. включает автозапуск `wg-quick@wg0` и поднимает службу;
8. проверяет себя: транзит включён, порт слушается — иначе завершается с ошибкой.

Повторный запуск ничего не ломает: ключи и конфиг с клиентами не перезаписываются.

## Порядок запуска

```bash
cd ~/main/vpn-server
chmod +x *.sh                    # git не хранит бит запуска
sudo ./install-wireguard.sh
```

`sudo` спросит пароль. Чтобы им не заниматься каждый раз, есть обёртка `webui-vpn` —
см. раздел «Беспарольный доступ для агента» ниже; тогда установка и выдача клиентов
делаются без вашего участия.

Если внешний адрес определился неверно (сервер за NAT провайдера) — задать вручную:

```bash
sudo WG_ENDPOINT=46.8.178.196 ./install-wireguard.sh
```

Вместо адреса можно указать имя — `WG_ENDPOINT=mokeevasky.ru`. Так лучше: сменится
адрес сервера — конфиги клиентов останутся годными.

Затем завести клиента на каждое устройство — свой, не общий:

```bash
sudo ./add-client.sh notebook --out /home/mokeeva/main/exchange/vpn
sudo ./add-client.sh phone
```

* `notebook` — файл `exchange/vpn/notebook.conf`, забрать по SFTP и открыть
  в клиенте WireGuard («Импорт туннеля из файла»). Каталог `exchange/` не
  версионируется — закрытый ключ в git не попадёт;
* `phone` — в терминале печатается QR-код, приложение WireGuard на телефоне
  сканирует его: «+» → «Сканировать QR-код». Переносить файл не нужно.

Отзыв доступа (устройство потеряно, человек больше не работает):

```bash
sudo ./remove-client.sh --list     # кто заведён
sudo ./remove-client.sh phone      # отключается сразу, не дожидаясь перезапуска
```

## Проверки после установки

Прежде чем считать, что работает, — пройти все пять. Первые три на сервере
(пройдены 12.09.2026):

```bash
sudo systemctl is-active wg-quick@wg0    # active
sudo webui-vpn status                    # интерфейс, порт, список пиров
ss -lnu | grep 51820                     # порт слушается
cat /proc/sys/net/ipv4/ip_forward        # 1, транзит включён
```

Две — на клиенте, **после подключения туннеля**; вот их и не хватает:

1. `curl https://api.ipify.org` (или сайт «мой IP» в браузере) показывает адрес
   **сервера**, а не домашний. Показывает домашний — трафик идёт мимо туннеля;
2. открывается любой сайт и `ping 10.8.0.1` доходит. Пинг доходит, а сайты нет —
   дело в пункте 4 установки (транзит) или в DNS, смотреть раздел ниже.

Отдельно стоит проверить, что **отзыв действительно отключает**: отозвать тестового
клиента и убедиться, что с него перестало ходить. Проверка, которая не падала на
сломанном, ничего не доказывает.

## Панель в веб-интерфейсе

Вкладка **VPN** между «Проекты» и «Настройки» (`webui/app/routers/vpn.py`,
`templates/vpn.html`). Там всё то же, что делают скрипты, только мышью: завести
клиента, показать его QR-код, скачать `.conf`, отозвать доступ, посмотреть
трафик и время последней связи по каждому клиенту. Числа обновляются сами раз
в 10 секунд, страницу перезагружать не нужно.

Панель не трогает `/etc/wireguard` и не зовёт `wg`: всё идёт через ту же обёртку
`webui-vpn`. Трафик берётся командой `peers` — это `list-peers.sh`, он сшивает
имена из конфига сервера с показаниями `wg show ... dump` по открытому ключу.

**QR-код и файл `.conf` содержат закрытый ключ устройства.** Оба маршрута
закрыты тем же входом, что и остальные страницы, кэширование выключено, а имя
клиента сверяется с образцом до всякого обращения к диску — иначе `?name=../..`
отдал бы через панель любой файл пользователя.

## Беспарольный доступ для агента

Чтобы агент мог ставить сервер и заводить клиентов сам, есть обёртка
`infra/webui-vpn.sh`. Ставится она **вашим** разовым шагом, с паролем:

```bash
sudo bash ~/main/infra/install-root-helpers.sh   # обёртка + root-овая копия скриптов
sudo bash ~/main/infra/apply-sudo.sh             # применить список разрешённых команд
```

После этого доступны беспарольно:

```bash
sudo webui-vpn install [--port ЧИСЛО]
sudo webui-vpn add ИМЯ [--split]     # конфиг ляжет в exchange/vpn
sudo webui-vpn remove ИМЯ
sudo webui-vpn list
sudo webui-vpn status
```

**Как это сужено.** Набор команд закрыт, произвольные доводы не проходят: имя
клиента сверяется с образцом (первым знаком буква или цифра — иначе `--help` и
любой другой флаг прошёл бы как имя), порт обязан быть числом 1…65535, каталог
выдачи задан жёстко. Обёртка запускает не скрипты из `vpn-server/` — этот каталог
доступен на запись пользователю и агенту, и запуск оттуда от root был бы просто
беспарольным root, — а их копию в `/usr/local/lib/webui-vpn`, принадлежащую root;
владельца и права копии она проверяет перед каждым запуском.

**Чего это не скрывает.** Установка пишет в `/etc` и правит `iptables` — по
существу это root-шаг, сужённый до одного дела. И выданный конфиг клиента лежит
в `exchange/vpn` с закрытым ключом: кто получил учётную запись `mokeeva`, тот
получил и доступ к самому VPN.

**Правка скриптов после установки обёртки требует повторного шага.** Работает
root-овая копия, а не файл в репозитории; чтобы новая версия заработала, снова
нужен `sudo bash infra/install-root-helpers.sh`.

## Проверка скриптов без сервера

```bash
./tests/check-clients.sh    # выдача, отзыв и сводка с трафиком
./tests/check-wrapper.sh    # разбор доводов в обёртке webui-vpn
```

Панель проверяется со стороны приложения:
`cd ~/main/webui && .venv/bin/python tests/check_vpn_panel.py`.

Заводит поддельный `/etc/wireguard` во временном каталоге, подделывает root через
`fakeroot` и подменяет `wg syncconf`/`wg-quick strip` заглушками — настоящими
остаются вызовы, считающие ключи. Систему не трогает, работающий сервер не нужен.

Проверяется: трое клиентов получают разные адреса; конфиг клиента сходится с
записью на сервере; открытый ключ на сервере отвечает закрытому у клиента; занятое
имя не принимается; отзыв убирает ровно одного пира и не рушит соседей;
освободившийся адрес выдаётся заново; `--split` сужает маршрут; имя с пробелом и
`;` отклоняется.

Проверка прогонялась на трёх дефектах, которые обязана ловить, и на каждом падала:
адрес выдаётся без учёта занятых (`beta` получает `10.8.0.2` вместо `10.8.0.3`);
отзыв вычищает файл до конца (`отзыв beta унёс gamma`); занятое имя не проверяется.

`check-wrapper.sh` проверяет разбор доводов обёртки: неизвестные команды, имена с
пробелом, `;`, путём, флагом и подстановкой, чужие ключи, негодный порт, работу без
root — и что годные доводы доходят до рабочих скриптов **дословно**. Запуск при этом
не происходит: `WEBUI_VPN_CHECK=1` велит обёртке показать разобранную команду и выйти.

Дословная сверка появилась не сразу и не зря. Первый вариант считал отказом любой
ненулевой код возврата — и прошёл зелёным на обеих внесённых дырах: обёртка
пропускала негодный довод внутрь, спотыкалась там об отсутствующую копию и
жаловалась, а проверка засчитывала это за отказ. Прогон на дефекте её и уличил.
Нынешний вариант падает на четырёх дырах: имя не проверяется, `install` принимает
любые доводы, каталог выдачи не передаётся, проверки root нет. Заодно он нашёл
настоящую дыру в образце имени — `--help` проходил как имя клиента.

## Если не работает

**Клиент не подключается вообще (нет рукопожатия, `latest handshake` пуст).**
По порядку:

1. брандмауэр **у хостера**, в личном кабинете VPS — отдельный от `ufw` на самой
   машине. Порт `51820/udp` должен быть открыт там тоже;
2. `ufw status` на сервере — если включён, должно быть `51820/udp ALLOW`;
3. сеть клиента режет UDP. Проверяется сменой сети (мобильный интернет вместо
   Wi-Fi). Лечится переносом сервера на порт `443/udp` — его режут реже:

   ```bash
   sudo WG_PORT=443 ./install-wireguard.sh
   ```

   С nginx конфликта нет: тот слушает 443 по TCP, а это UDP. Клиентам после смены
   порта нужны новые конфиги (в старых прописан прежний порт).

**Рукопожатие есть, интернета нет.** Транзит или NAT:

```bash
sysctl net.ipv4.ip_forward                       # должно быть 1
sudo iptables -t nat -L POSTROUTING -n -v        # должна быть строка MASQUERADE
ip route show default                            # тот ли интерфейс в правилах
```

Частый случай — включённый `ufw`: у него правила транзита свои, и дописанное в
конец цепочки правило не срабатывает. В конфиге они поэтому вставляются в начало
(`-I FORWARD 1`). Если `ufw` включали после установки — перезапустить `wg-quick@wg0`.

**Сайты не открываются, а по адресу пингуются.** DNS. В конфиге клиента строка
`DNS = 1.1.1.1, 8.8.8.8`; на Linux-клиенте она требует пакета `openresolv` или
`resolvconf`, без него wg-quick ругается. Либо ставится пакет, либо строка убирается.

**Обрывы после простоя за NAT.** `PersistentKeepalive = 25` в конфиге клиента уже
стоит — он это и лечит.

## Про IPv6

Комплект настраивает только IPv4. Если у сервера есть IPv6, а у клиента тоже, то
запросы к сайтам с IPv6 пойдут **мимо туннеля**, с настоящего адреса — для «скрыть
адрес» это дыра, для «попасть в сеть сервера» безразлично. Самое простое лечение —
отключить IPv6 на клиенте. Полное — завести в туннеле ULA-сеть и второй MASQUERADE;
это отдельная задача, в скриптах её нет сознательно, чтобы не усложнять то, что
может и не понадобиться.

## Что где лежит

| Путь | Что |
|---|---|
| `/etc/wireguard/server.key`, `server.pub` | ключи сервера, 600, только root |
| `/etc/wireguard/wg0.conf` | интерфейс и список пиров |
| `/etc/wireguard/params` | параметры установки для скриптов |
| `/etc/wireguard/clients/*.conf` | выданные конфиги, в них закрытые ключи клиентов |
| `/etc/sysctl.d/99-wireguard.conf` | включение транзита |
| `exchange/vpn/*.conf` | копии для переноса по SFTP, вне git |

**Закрытые ключи в репозиторий не кладутся.** Скрипты пишут их только в
`/etc/wireguard` и, по ключу `--out`, в указанный каталог — для него и предназначен
неверсионируемый `exchange/`.

## Ограничения, о которых стоит знать заранее

* **Весь трафик клиента пойдёт через сервер** и наружу — с его адресом. Значит,
  весь он виден владельцу сервера (хостеру) и упирается в канал VPS: скорость
  будет не выше, чем у сервера, а задержка вырастет на дорогу до него. Если нужен
  только доступ к самому серверу и его службам, а не выход в интернет — заводите
  клиента с ключом `--split`;
* **сервер один, и он же обслуживает webui.** Скачивание торрентов и прочая
  нагрузка через тот же канал отразится на отзывчивости `https://mokeevasky.ru/Claude`;
* договор с хостером обычно разрешает личный VPN, но запрещает предоставлять его
  третьим лицам как услугу. Раздавать конфиги посторонним — риск для всего сервера,
  включая webui.
